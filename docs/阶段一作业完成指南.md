# 阶段一作业完成指南

本指南对应老师《作业指导》的报告1。当前任务是编写能分析整份约8.93 GB投诉CSV的Python程序，并用初步证据说明问题、范围和后续研究方向。报告1不是最终论文，也不要求现在就证明全新的算法。

## 一 本次确定的项目与范围

建议项目名称：**大规模金融投诉数据的流式分析与异常线索发现**。

问题陈述：给定老师提供的本地投诉CSV，系统在不整体载入原始文本的情况下，生成可复现的质量诊断、类别/时间汇总、明确分母的指标和校验结果，帮助研究者发现值得进一步核查的投诉变化。后续阶段再在稳定分类口径的月度聚合上比较异常检测方法。

阶段一覆盖全文件，不限制为支票/储蓄账户，也不以赔付预测为主任务。前面讨论的文本样本偏差保留为后续研究方向。阶段一不训练AI模型；指导第3页明确允许数据解析器或最小处理流水线作为原型。指导第7–12、21页要求后续AI方法比较、集成和评估，因此保留异常检测路线供教师审批。

## 二 报告1应交什么

依据指导第1–4页，提交包包括：

1. PDF报告：正文4–6页，参考文献及附录不计页数，正文10–12磅、边距至少2厘米，图表编号并在文中解释。
2. 项目Git仓库的固定commit或tag链接。最终提交标签使用`phase-1-submission`，不能只给会继续变化的分支主页。
3. 可执行的Python代码、测试、配置/依赖说明、小样本或数据访问方法。
4. 可复现的图表和运行证据。
5. 真实的个人贡献声明、生成式AI及外部资源使用说明。
6. 首次报告说明暂无上一阶段反馈；以后逐条记录如何修改。

报告文件最终命名为`实际团队名_phase1_report.pdf`。当前团队名、成员、远程仓库和截止日期尚未确定，草稿里的待填项必须由你补齐。不得填入虚构团队成员或不存在的仓库地址。

## 四 哪些代码放正文 哪些放仓库

**正文放两段短代码即可。** 第一段展示使用`csv.reader(..., strict=True)`处理带引号、逗号和换行的记录，并检查字段数。第二段展示分母为零如何处理，以及频数/交叉表如何与总记录数对账。代码应服务于解释设计，避免整页代码和代码截图。

完整实现和测试放仓库：

| 文件 | 学生应能解释的内容 |
| --- | --- |
| `complaints_analyzer/core.py` | 为什么不能用`split(',')`；如何逐条读取；计数器保存什么；ID位块怎样查重；为什么不直接删重复行 |
| `complaints_analyzer/reporting.py` | 如何从聚合值生成报告；如何防止将空分母写为0% |
| `complaints_analyzer/__main__.py` | 参数如何进入系统；输出覆盖防护；错误如何退出 |
| `tests/test_analyzer.py` | 每个测试针对哪种实际风险；预期值如何人工确定 |
| `scripts/make_demo.py` | 合成数据为什么可公开；它不是真实研究样本 |
| `scripts/verify_reference.py` | 新程序如何与独立控制值比较 |
| `scripts/reference_pandas.py` | 可选的独立分块参考实现；核心程序不依赖它 |
| `scripts/build_report.py` | 如何由实测证据重新生成PDF与图表 |
| `README.md`、依赖文件 | 别人如何在自己的机器上重现 |

`evidence/`存放本次聚合结果、测试日志、源文件SHA-256和交叉验证证据。原始8.93 GB文件和原始投诉叙述不要上传Git仓库。

## 五 提交前你需要亲自完成的操作

先解压代码包，在项目根目录打开终端，确认机器安装Python 3.10或以上，然后执行：

```powershell
python -m unittest discover -s tests -v
python scripts/make_demo.py
python -m complaints_analyzer data/synthetic_complaints.csv --outdir results/demo
python -m complaints_analyzer "E:/QQ/complaints.csv/complaints.csv" --outdir results/full --batch-size 500000
python scripts/verify_reference.py results/full/summary.json
```

若第一次担心等待时间，可先用`--limit 10000`调试，但受限运行不能作为全量实验证据。完整运行用UTF-8/UTF-8 BOM输入，处理的是带引号规则的逻辑记录。

逐项核验：

- 合成例应有12条记录、9条及时回应、6条非空叙述、3条金钱救济。
- 真实文件应得到16,545,376条记录；如文件换版，必须先核对源文件指纹，不能强行把新结果改成旧数字。
- 阅读测试结果和`results/full/analysis.md`，说明及时回应率为什么不是解决率。
- 用自己的话解释扫描时间与内存、文本缺失、ID缺失、日期倒置分别意味着什么。
- 至少亲自修改一个有意义的部分或增加一个有明确风险动机的测试，并记录自己的贡献。不要为了凑提交次数制造修改。
- 补齐团队、成员、日期、真实个人分工与仓库链接。创建自己的仓库并上传代码、合成数据和聚合证据。
- 本地代码中的`phase-1-draft`只是AI辅助草稿版本。学生完成修改与复现后创建`phase-1-submission`，同步更新PDF里的commit/tag。
- 按指导第26页公开AI参与的任务、采用的材料、学生实际验证内容。不能把助手运行写成学生本人已完成。

## 六 创新点如何写才准确

指导第13、18页明确：课程创新可以是有依据的集成、新评估、领域适配或有意义的系统扩展，不要求发表级算法创新。

本项目可写的**当前工程特点**：将流式解析、精确ID诊断、统计口径、全量/部分标记、结果对账和可复现证据整合在同一个低依赖程序中，并在实际大文件上验证。不要写“首次发明流式分析”“全球首次用AI分析投诉”或“比所有工具更快”，因为没有这类证据。

可写的**后续研究问题**：只保留有叙述的记录后，产品/企业回应分布和异常月份排序会改变多少？按可观测构成调整后，差异还在不在？程序能否把分类断点和未完整月份提示出来，从而减少误报？这是待检验问题，不是阶段一已经成立的结论。

“以前没人想到”不能作为创新声明。相关研究已经讨论投诉公开与选择偏差；本项目可贡献的是在这份具体数据上进行新的可复现比较并量化影响。

## 七 后续四阶段的详细路线

**阶段二，第6节课结束：数据与实验设计。** 固定数据版本、观察单位、字段字典和原标签变更记录；明确哪些产品序列在同一口径下有足够历史；排除未完整月份参与直接比较；预先规定时间训练/验证/测试划分、随机种子、规则基线、指标和人工复核办法。完成缺失、标签质量与隐私说明。正式切分在看测试结果前固定。

**阶段三，第10节课结束：比较建模。** 比较至少三类方法：滚动中位数/MAD规则基线、可解释统计模型、Isolation Forest等非线性AI方法。使用相同范围和时间划分。拟用特征包括当前计数相对历史的变化、份额及质量指标；所有变换只用训练/历史信息拟合。报告误报、遗漏、运行成本、子组差异和至少一项消融。若无真实异常标签，人工核查和合成异常注入分开报告；不能把“原样本都正常”作为未经验证的事实。

**阶段四，第13节课结束：集成系统。** 将CSV加载、质量检查、统计、模型与结果解释连成CLI或本地界面，支持新文件；展示正常输入、困难但有效输入、错误/拒绝输入三类案例；加入端到端测试、延迟记录与异常恢复。直接重放静态图表不等于完成系统。

**阶段五，第16节课结束：受控扩展与综合。** 只选择一个明确扩展，优先“文本覆盖及分类断点提示/敏感性审计”；比较有无扩展时的人工复核结果、异常排序和误报情况；记录帮助和未帮助的案例。加入数据漂移监控、版本/回滚与最终答辩计划，逐条回应阶段反馈。

若教师不批准异常检测路线，应在阶段一之后调整后续AI任务，不应为了套用模型而忽略原来的数据分析需求。
